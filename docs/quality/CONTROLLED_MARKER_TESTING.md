# 受控标记肿物识别测试与反馈规则

本文件用于后续总指挥和测试执行者。它不改变算法、RSTL 或人工操作界面。

## 1. 四种证据要分开

- **流程证据**：页面能打开、图片能载入、按钮能触发。
- **识别证据**：日志绑定了原图、运行身份和检测结果，能说明是否生成候选、是否闭合、是否误报。
- **视觉证据**：截图显示用户最终看到的边界。
- **边界准确性证据**：需要人工参考边界或明确人工确认。没有这项时，只能说“候选已生成”，不能说“边界准确”。

## 2. 自动化测试的固定顺序

1. 先读取 `/__runtime-identity.json`，确认 profile、实现版本、源码指纹和开发者模式一致。
2. 检查输入文件哈希和尺寸；不一致就标为 `input_or_binding_invalid`，不算算法失败。
3. 使用单 worker、串行样本和每样本超时；超时只终止本轮测试创建的进程。
4. 等待真实业务事件（受控标记终态和诊断事件），不等待隐藏状态节点“可见”。
5. 每张图保存原始诊断 JSON、最终页面截图和样本状态。
6. 样本状态必须区分：`success`、`algorithm_failure`、`harness_invalid`、`environment_failure`、`excluded`、`untested`。
7. 运行身份变化、诊断事件缺失或测试脚本自身报错时，优先标为 `harness_invalid`，不得把它写成算法失败。
8. 正常对照、无肿物对照和独立留出样本不能因调参而被跳过。

## 3. 日志能证明什么

诊断记录应保留：运行编号、来源哈希、输入尺寸、profile/版本/源码与资产身份、入口和时间、结果状态、候选数量、边界点数、闭合状态、面积/外接框、失败原因及丢弃计数。

日志中的 `evidence_state` 含义：

- `ready_for_review`：记录完整，可以人工查看；不等于边界准确。
- `detector_failed`：检测器明确失败。
- `input_or_binding_invalid`：输入或来源绑定无效，不计入算法成败。
- `runtime_identity_mismatch`：运行身份不一致，本轮验收作废。
- `evidence_incomplete`：证据不完整，暂停依赖它的结论。

日志不保存原图，不把文件路径、个人信息或人工医学结论写入公共诊断记录。

## 4. 人工反馈的最小格式

操作者只需：

1. 发现错误时，发送 1～2 张最典型截图；相同错误不用全部发送。
2. 用一句短话选择现象：漏检、未闭合、边界变形、偏大/偏小/偏移、误报、紫线跑出、不确定或其他。
3. 不需要发送正确图片，不需要手工分析日志。
4. 不知道样本名时写“样本名不确定”。系统不得猜测绑定；必要时只向操作者确认一次。

截图只作为人工观察证据，不能覆盖或替代原图。

## 5. 收到反馈后的处理顺序

1. 先排查测试工具，再排查环境、输入、产品流程，最后才判断算法。
2. 证据不足时补观测，不直接改算法。
3. 确认算法问题且已有本轮修改授权时，先保存当前可恢复版本，再做最小修改。
4. 修改后必须复测原失败样本、正常对照和独立留出样本。
5. 两次近似修补没有改善，就停止叠加补丁，重新检查复现条件和根因假设。
6. 最终只能报告证据支持的范围，不把工程测试写成临床结论。

## 6. 本项目已知教训

本项目曾出现：测试脚本等待隐藏节点可见，导致 5 张图片被误判为无效；同时过去把“日志显示识别成功”和“截图出现闭合线”近似当成了“边界准确”。今后这两类问题必须分别记录并立即反馈给操作者。
